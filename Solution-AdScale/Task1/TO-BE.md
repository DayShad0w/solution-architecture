# TO-BE. Целевая архитектура AdScale

Два рисунка, потому что «через 3 месяца» и «через год» — разные системы:

- переход: [diagrams/c4-container-transition-3m.puml](diagrams/c4-container-transition-3m.puml);
- цель года: [diagrams/c4-container-to-be.puml](diagrams/c4-container-to-be.puml).

Решения, которые это фиксирует: [ADR-001](adr/ADR-001-evolution-strategy.md), [ADR-002](adr/ADR-002-bidding-service-first.md), [ADR-003](adr/ADR-003-event-streaming.md).

## Принципы

1. Горячий путь ставки не вызывает PostgreSQL, финансовый сервис и Kafka синхронно.
2. Критичный трафик DSP и некритичный трафик кабинета входят через разные двери.
3. У каждого сервиса своя система учёта. Общая база монолита — временное состояние, а не образец.
4. Новый партнёр садится на новый путь. Старые партнёры переезжают после паритета, а не в ту же ночь.
5. Отказ от ставки — штатный успешный исход, если данных не хватает или бюджет времени исчерпан.
6. Деньги списываются по идемпотентным событиям показа, а не «заодно» внутри ответа аукциона.

## Что будет через 3 месяца

Цель среза — не микросервисная платформа, а отдельный контур под новый договор.

```text
Новая DSP
  → Envoy (mTLS, лимит частоты, таймаут, размыкатель)
    → Bidding Service
        читает кандидатов и бюджет из L1 и Redis
        отвечает 200 или 204
        после ответа кладёт событие в Kafka
Старая DSP и кабинет
  → прежний монолит
Проектор
  → читает кампании и бюджеты из PostgreSQL монолита
  → обновляет Redis
Аналитика кабинета
  → read replica PostgreSQL, не primary
```

В эти три месяца отдельные сервисы кампаний, финансов и аналитики ещё не выпускаются. Их данные проецирует антикоррупционный адаптер поверх монолита. Так команда тратит срок на SLA партнёра, а не на распил кабинета.

Состав первой поставки:

| Компонент | Зачем в первой поставке |
| --- | --- |
| Envoy как RTB-шлюз | Единственная дверь нового партнёра: аутентификация, лимит, таймаут, метрики |
| Bidding Service | Ответ за десятки миллисекунд без синхронной БД |
| Redis | Проекция кампаний, креативов и остатка бюджета |
| Управляемый Kafka | Снять запись показов и кликов с primary PostgreSQL на новом пути |
| Tracking Ingress | Тонкий приём показа, клика и win-notice, сразу в очередь |
| Проектор из монолита | Наполнить Redis, не дожидаясь сервиса кампаний |
| Read replica | Убрать тяжёлые отчёты с primary ещё до ClickHouse |
| Монолит как был | Текущие рекламодатели и старые DSP |

Критерий готовности среза: нагрузочный прогон нового пути на 18 000 RPS, P95 ≤ 80 ms, старый путь не хуже текущего базового уровня, расхождение правил аукциона со shadow-прогоном в допуске (см. план ниже).

## Что будет через год

Монолит распадается по уже существующим ролям. Новые площадки подключаются к тому же шлюзу.

### Границы сервисов

| Сервис | Ответственность | Почему граница именно здесь |
| --- | --- | --- |
| RTB API Gateway (Envoy) | Внешний OpenRTB: TLS, личность партнёра, лимит, таймаут, размыкатель, метрики latency | Меняется реже, чем аукцион, и должен уметь ответить no-bid, когда сервис ставок болен |
| Bidding Service | Разбор bid request, отбор кандидатов, аукцион, bid response | Единый горячий путь. Резать Ad Server и Auction Engine сетевым вызовом нельзя: лишний hop съедает бюджет 80 ms |
| Tracking Ingress | Приём показа, клика, win-notice | Другой профиль нагрузки и другой SLA, чем у аукциона |
| Campaign Service | Кампании, таргетинг, ставки, метаданные креативов. Система учёта рекламы | Жизненный цикл рекламодателя, а не цикл одной ставки |
| Creative Delivery | Сборка HTML/JS в момент сохранения креатива, выкладка в кэш | Сборка баннера уходит с горячего пути |
| Finance Service | Балансы, счета, пополнение через платёжный шлюз, идемпотентный журнал списаний | Деньги требуют ACID и отдельного доступа. Кабинет больше не ходит в шлюз оплаты напрямую |
| Analytics Service | Запросы отчётов | Только колоночное хранилище, никогда primary учёта |
| Advertiser Cabinet | UI и BFF кабинета | Человеческий трафик. Свой вход, не RTB-шлюз |

Статистика как отдельная запись в PostgreSQL исчезает. Её место занимают поток событий и загрузчик в колоночное хранилище. Подробности хранилищ — в задании 3.

### Как сервисы говорят друг с другом

На горячем пути сетевых зависимостей нет: Bidding Service читает локальную память и при промахе Redis.

Вне горячего пути:

- кабинет → Campaign, Finance, Analytics по HTTPS/JSON (люди, секундные операции);
- Finance → платёжный шлюз по API шлюза;
- изменения кампаний и исчерпание бюджета → Kafka, подписчики обновляют Redis;
- показы и клики → Kafka → загрузчик статистики и финансовый потребитель;
- прогрев и снимок кандидатов → пакетное чтение у Campaign Service, не на каждый bid request.

Брокер — Kafka. Кэш — Redis Cluster плюс L1 в каждом процессе ставок. Подробное обоснование протоколов — в [Task2/interaction.md](../Task2/interaction.md).

### Данные на целевой схеме

| Сервис | Хранилище |
| --- | --- |
| Bidding | Без своей БД учёта. L1 + Redis, журнал решений уходит в поток |
| Campaign | PostgreSQL |
| Finance | PostgreSQL |
| Tracking / статистика | Kafka как буфер, ClickHouse как учёт событий |
| Analytics | ClickHouse (отдельная база, свои витрины) |
| Cabinet | Не хранит доменных данных |

Один PostgreSQL на всех больше не используется.

### Инфраструктура года

- Kubernetes как среда stateless-сервисов (ставки, шлюз, приём событий, API кабинета).
- Управляемые PostgreSQL, Redis и Kafka.
- Два региона: ставки активны в обоих, финансы — активный/пассивный с синхронной репликой журнала, конфигурация кампаний копируется между регионами потоком.
- Метрики, логи и трассы горячего пути обязательны до включения боевого партнёра, а не «после стабилизации».

SLA контура ставок — 99,9%. Мультиплатформенность — это тот же OpenRTB-вход и та же проекция кандидатов, с отдельным лимитом и ключом на партнёра, а не отдельная система.

## Почему границы горячего пути такие тесные

Ad Server, Auction Engine и сборка ответа остаются одним процессом Bidding Service. Это сознательное отступление от «один модуль — один сервис». Сетевой вызов между подбором кандидата и аукционом добавил бы миллисекунды и новую точку таймаута на участке, который уже не укладывается в SLO.

Доставка разметки, наоборот, выносится: баннер зависит от кампании, а не от конкретного bid request. Его можно собрать заранее.

Запись статистики выносится по другой причине: ей нужна надёжная доставка, а ставке нужно успеть ответить. Общая транзакция тут вредна.

## План перехода

| Окно | Шаг | Зачем так |
| --- | --- | --- |
| Недели 1–3 | Метрики P95 монолита, read replica для отчётов, управляемые Redis и Kafka, проектор кампаний и бюджетов | Сначала убрать чужую нагрузку с primary и наполнить кэш |
| Недели 2–6 | Bidding Service в shadow mode: копия запросов, ответ партнёру не отдаётся, сравнение с текущим движком | Проверить правила аукциона до боевого SLA |
| Недели 6–8 | Envoy и боевой трафик только новой DSP. Старые DSP остаются на монолите | Шов совпадает с новым договором |
| Недели 6–10 | Tracking Ingress и потребители Kafka для нового пути | Показы новой интеграции не пишутся в primary синхронно |
| Недели 8–12 | Нагрузочный прогон 18 000 RPS, прогон отказа Redis и отказа копии ставок, короткие инструкции дежурному | Сдать интеграцию можно только с доказанным хвостом latency |
| Месяцы 4–8 | Campaign Service и перевод проектора с монолита на него. Creative Delivery в офлайне | Система учёта рекламы отделяется, когда горячий путь уже стабилен |
| Месяцы 6–10 | Finance Service, идемпотентный журнал, платёжный шлюз только через него | Деньги переезжают отдельным релизом со сверкой |
| Месяцы 8–12 | ClickHouse, отключение аналитики от PostgreSQL, второй регион, перевод старых DSP на новый путь, выключение аукциона в монолите | Финальные 50 000 RPS и 99,9% |

Откат любой волны — переключить партнёра обратно на монолит на шлюзе. Пока старый путь жив, это основной план отката, а не резервная копия базы.

## Риски целевой схемы

| Риск | Что делаем |
| --- | --- |
| Порт правил аукциона ошибается | Shadow mode и корпус пар «запрос — ответ» со старого движка |
| Устаревший бюджет в Redis, перекрут | Короткий TTL остатка, консервативный pacing, жёсткая остановка кампании событием, сверка журнала |
| Команда не вывозит Kubernetes и Kafka сразу | В первые три месяца мало сервисов и управляемый брокер. Свой «платформенный» слой не строим |
| Двойное списание при повторе событий | Идемпотентность по идентификатору показа. См. задание 2 и 3 |
| Второй регион усложнит деньги | Финансы не делаем active-active в этом горизонте |

## Что сознательно не входит в цель года

- Перепис всех четырёх языков в один.
- Собственный сервис сессий и DMP. Профиль пользователя на горячем пути — кэш, источник уточняется отдельно, когда появится контракт на сегменты.
- Потоковый фреймворк класса Flink. Потребителей Kafka достаточно для загрузки хранилища и журнала денег.
- Вынос кабинета в микрофронтенды. Для SLA партнёра это не драйвер.
