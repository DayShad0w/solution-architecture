# ADR-003. Выбор технологии для потоковой обработки событий: Apache Kafka и Avro

- Статус: принято
- Дата: 2026-09-23

## Контекст

Показы и клики сейчас записываются напрямую в тот же PostgreSQL, что обслуживает аукцион. Буферизация отсутствует. После интеграции объём событий вырастет пропорционально трафику, а через год платформа должна выдерживать пик в 50 000 RPS. События нужны сразу нескольким потребителям: загрузчику статистики, финансовому журналу, механизму сверки, а позже — витринам аналитики. Любой из потребителей может отстать или упасть и должен иметь возможность дочитать пропущенные сообщения, а не потерять их.

При этом горячий путь аукциона не может ждать подтверждения записи в хранилище учёта.

## Решение

События показов, кликов и win-notice публикуются в Apache Kafka. Для сериализации используется Avro с реестром схем. Политика совместимости — обратная (backward): потребители старой версии игнорируют новые поля.

Публикация события аукциона с горячего пути не блокирует HTTP-ответ партнёру. Журнал аукциона, если он нужен для разбора инцидентов, записывается уже после отправки ответа — из памяти процесса, через локальный буфер с ограниченным размером.

Учёт денег опирается не на этот необязательный журнал аукциона, а на события показа и клика. Их Tracking Ingress записывает в Kafka и дожидается подтверждения брокера до ответа трекинговому пикселю. Два принципа работают одновременно: потерять факт показа нельзя, но и задерживать ответ аукциона ради журнала аукциона нельзя. У этих операций разные требования к надёжности.

Детальное описание топиков, ключей и групп потребителей приведено в [Task3/event-streaming.md](../../Task3/event-streaming.md).

Kafka используется как управляемый сервис.

## Альтернативы

### Продолжить запись в PostgreSQL, но пакетами

Отклонено. Пакетная запись уменьшает число фиксаций, но хранилище остаётся общим с аукционом. Нескольким независимым потребителям невозможно читать историю событий с разной скоростью, а механизм повторной обработки после сбоя загрузчика в такой модели отсутствует.

### RabbitMQ

Отклонено для данного потока. Классическая очередь задач хорошо подходит для сценариев «выполни и забудь». Здесь же нужен журнал с хранением истории: несколько подписчиков, возможность повторной загрузки в колоночное хранилище, допустимость отставания финансового потребителя на минуты без потери данных. Это модель распределённого лога, а не очереди задач.

### Redis Streams

Отклонено в качестве основного журнала событий. Redis в этой архитектуре уже выполняет роль кэша проекций и остатков бюджета. Совмещение кратковременного кэша и многодневного журнала событий в одном кластере означает, что их отказы и потребление памяти будут связаны. Для объёмов, ожидаемых через год, нужен полноценный брокер с настраиваемым сроком хранения и несколькими группами потребителей, а не надстройка над кэшем.

### JSON без реестра схем

Отклонено для критичных потоков данных. JSON проще на старте, но при нескольких командах-потребителях и постепенном изменении полей события нарушает совместимость без явного предупреждения. Avro и реестр схем фиксируют контракт между продюсером и потребителями. Для административных низкочастотных сообщений можно было бы оставить JSON, но единый формат для всех топиков проще сопровождать для команды без выделенной платформенной группы.

### Отдельный Flink-кластер для потоковой обработки

Отклонено на текущем горизонте. Необходимые агрегации закрываются потребителями Kafka и материализованными представлениями в ClickHouse. Ещё один распределённый движок без SRE обойдётся слишком дорого в эксплуатации.

## Последствия

Плюсы:

- запись событий больше не конкурирует с чтением ставок за ресурсы PostgreSQL;
- финансовый журнал и загрузчик аналитики читают один и тот же поток с разной скоростью, не мешая друг другу;
- повторная загрузка данных в хранилище статистики выполняется перемоткой offset, а не восстановлением из резервной копии.

Минусы:

- появляется брокер, за которым нужно следить: лаг потребителей, заполнение диска, совместимость схем;
- семантика доставки at-least-once требует, чтобы все потребители были идемпотентными;
- управляемый сервис стоит денег, но это дешевле, чем содержать собственный кластер без выделенной дежурной смены.

Операционный минимум: фактор репликации 3, `min.insync.replicas=2`, мониторинг лага потребителей и загрузчика на дашборде, оповещение при приближении лага к границе срока хранения.
