# Сервис ставок

Связанные решения: [ADR-002](../Task1/adr/ADR-002-bidding-service-first.md). Диаграмма компонентов: [diagrams/component-bidding.puml](diagrams/component-bidding.puml). Последовательность запроса: [diagrams/sequence-bid.puml](diagrams/sequence-bid.puml).

## Назначение

Bidding Service принимает OpenRTB-запрос от шлюза, выбирает объявление по проекции кампаний и возвращает bid response либо no-bid. Он же исполняет правила, которые сегодня живут в Auction Engine.

Сервис stateless относительно учёта: любую копию можно остановить, кампании от этого не пропадут. В памяти процесса лежит только воспроизводимая проекция и счётчики процесса.

## Что входит в границу

- проверка формы bid request и поля `tmax`;
- отбор кандидатов по площадке, формату, гео и устройству;
- частотное ограничение, если Redis ответил вовремя;
- применение бизнес-правил и выбор победителя;
- подстановка заранее собранной разметки (`adm`) из проекции;
- решение «ставить / не ставить» с причиной no-bid для метрик;
- оценка остатка бюджета по кэшу (pacing), без проводки в журнале денег.

## Что не входит

| Задача | Кто делает | Почему не сервис ставок |
| --- | --- | --- |
| Система учёта кампаний | Campaign Service, на переходе — монолит через проектор | Другой цикл изменений и другая база |
| Сборка HTML/JS | Creative Delivery при сохранении креатива | Нельзя тратить горячий путь на шаблоны |
| Приём показа и клика | Tracking Ingress | Другой SLA и другая гарантия доставки |
| Списание и счета | Finance Service | Нужен ACID и идемпотентный журнал |
| Отчёты | Analytics Service | Тяжёлые чтения |
| mTLS, лимит партнёра, отсечение больного апстрима | RTB API Gateway | Должно работать, даже если процесс ставок не успевает |

## Контекстная зависимость

```text
DSP → API Gateway → Bidding Service → L1 / Redis
                         │
                         └─ после HTTP-ответа → Kafka (журнал аукциона, best effort)

Проектор / Campaign Service → Redis   (вне запроса)
Finance → Kafka → Redis              (стоп бюджета и остаток)
Tracking Ingress → Kafka → Finance   (факт списания)
```

Синхронных обязательных зависимостей на запросе нет. Redis — необязательная зависимость: промах или таймаут Redis не удлиняет ответ сверх дедлайна (см. [reliability.md](reliability.md)).

## API

### Внешний контракт, через шлюз

Сервис не опубликован в интернет сам. Снаружи виден только шлюз.

`POST /openrtb/2.6/bid`

- тело: OpenRTB 2.6 BidRequest (JSON);
- успех со ставкой: `200` и BidResponse;
- штатный отказ: `204` без тела;
- кривой запрос: `400` (шлюз может отрезать ещё раньше).

В ответе со ставкой обязательны `id` исходного запроса, `impid`, `price`, `adm`, `crid`, `nurl` и адрес биллинга показа. `nurl` и пиксель показа ведут на Tracking Ingress, не обратно в сервис ставок.

Сервис уважает `tmax`: дедлайн обработки = `min(бюджет_партнёра, tmax − запас_сети)`. Если дедлайн меньше 15 ms, сразу `204`: честный аукцион уже не успеть.

Идентификатор запроса партнёра используется как ключ идемпотентности ответа на шлюзе в коротком окне (единицы секунд), чтобы повтор того же `id` не запускал второй аукцион.

### Внутренний административный API

Не участвует в ставке. Нужен для прогрева и диагностики.

| Вызов | Назначение |
| --- | --- |
| `GET /health/live` | Процесс жив |
| `GET /health/ready` | Проекция прогрета, процесс принимает трафик |
| `GET /debug/nobid-counters` | Счётчики причин отказа за интервал, только из внутренней сети |

Пакетное обновление проекции процесс не принимает по RPC на каждый запрос. Проектор пишет в Redis, процессы ставок читают Redis и держат L1. Отдельный `GetCampaign` на горячем пути запрещён.

### События наружу

После отправки HTTP-ответа процесс может опубликовать `rtb.auction` (выборка, не каждый из 50 000 RPS). Это журнал для разбора, не источник денег. Контракт денег — события Tracking Ingress, [задание 3](../Task3/event-streaming.md).

## Модель данных

Системы учёта у сервиса нет. Есть денормализованная запись кандидата, которую собирает проектор.

### BidCandidate (Redis и L1)

| Поле | Смысл |
| --- | --- |
| `line_item_id` | Ключ кандидата |
| `campaign_id`, `advertiser_id` | Связь с учётом и бюджетом |
| `creative_id`, `adm`, `w`, `h` | Готовая разметка и размер |
| `max_bid` | Потолок цены |
| `targeting` | Площадка, формат, гео, устройство, категории |
| `status` | active / paused |
| `budget_remaining_micros` | Оценка остатка, не бухгалтерский баланс |
| `daily_cap_micros` | Суточный потолок для pacing |
| `updated_at` | Версия проекции |

Ключи Redis:

- `cand:{line_item_id}` — запись кандидата;
- `idx:{partner}:{format}:{geo}` — список идентификаторов для отбора без перебора всех кампаний;
- `budget:{campaign_id}` — остаток для pacing;
- `freq:{user_key}:{campaign_id}` — счётчик частоты с TTL;
- `stop:{campaign_id}` — флаг жёсткой остановки, его наличие запрещает ставку.

Индекс и кандидаты пересобираются из снимка. Потеря Redis не теряет кампании: снимок лежит в системе учёта.

### Что считается на лету и не хранится

Победитель, цена этой ставки, причина no-bid. В учётную базу это не пишется. Причины копятся в метриках процесса. Выборка аукционов уходит в Kafka.

### Бюджет на горячем пути

Сервис не проводит проводку. Он только решает, можно ли ещё ставить.

- Если остаток большой, процесс использует значение из L1, обновляемое раз в 1 секунду.
- Если остаток близок к суточному потолку, процесс делает атомарную проверку в Redis и при отказе Redis не ставит (fail closed для денег).
- Факт списания делает Finance Service по событию показа. Пока событие не дошло, pacing занижает доступный остаток на ожидаемую долю побед, чтобы короткое отставание потребителя не перекручивало бюджет.
- Событие `budget.exhausted` выставляет `stop:{campaign_id}`. Такие кампании выпадают из индекса сразу, не дожидаясь TTL.

Так аукцион не ждёт финансовую транзакцию, а незамеченный перекрут ограничен окном pacing, а не всей суточной кассой.

## Конвейер одного запроса

1. Шлюз передал запрос и дедлайн.
2. Разбор JSON и отсечение заведомо нерелевантных впечатлений (нет размера, нет площадки).
3. Поиск кандидатов в L1 по ключу индекса. При промахе — одно чтение Redis, если до дедлайна больше 10 ms. Иначе no-bid `cache_miss_deadline`.
4. Фильтр статуса, размера и `stop`.
5. Частота: одно чтение Redis. Таймаут 2 ms. Не ответил — ограничение пропускаем (fail open), ставку не задерживаем. Показ лишний допустим, сорванный SLA — нет.
6. Правила аукциона в памяти, выбор цены не выше `max_bid` и не выше того, что пропускает pacing.
7. Если победителя нет — `204` и счётчик причины.
8. Если есть — `200` с `adm` из проекции.
9. Уже после записи ответа в сокет — попытка отдать выборку в локальный буфер Kafka-продюсера. Переполнение буфера означает сброс выборки, не задержку клиента.

## Бюджет задержки (P95 нового пути)

| Участок | Бюджет |
| --- | --- |
| Шлюз: TLS уже снят, проверки | 4 ms |
| Сеть внутри зоны до процесса | 2 ms |
| Разбор и проверки | 3 ms |
| Индекс L1 | 2 ms |
| Redis, только промах L1 или тесный бюджет | до 4 ms |
| Аукцион в памяти | 6 ms |
| Сборка ответа | 2 ms |
| Запас на хвост | 15 ms |

Ориентир при тёплом L1 — уложиться около 40 ms по P95, с запасом до договорных 80 ms на сеть партнёра и `tmax`. Синхронный PostgreSQL в эту таблицу не входит: одно такое чтение с конкуренцией аналитики сегодня и даёт хвост 110–120 ms.

## Состояние готовности

Реплика не получает боевой трафик, пока не прогреет L1 снимком активных кандидатов из Redis. Прогрев — условие `readiness`, а не побочный эффект первого запроса пользователя. Иначе первая минута после выкладки была бы сплошным промахом в кэш под нагрузкой партнёра.

## Масштаб и выкладка

Копии не хранят уникальных данных. Масштаб — число процессов по CPU и RPS. Для среза 18 000 RPS закладываем не меньше двух зон доступности в одном регионе и снятие копии с балансировки шлюзом за секунды. Цель 50 000 RPS — те же процессы во втором регионе, без смены API.

Выкладка канарейкой по весу на шлюзе. Откат — вес обратно на монолит для этого партнёра, пока старый путь ещё жив.

## Наблюдаемость, без которой сервис не включают

- гистограмма времени до ответа, разрез partner / код ответа;
- доля `204` по причинам (`no_candidate`, `budget`, `freq`, `deadline`, `stopped`);
- доля промахов L1 и таймаутов Redis;
- возраст проекции (`now − updated_at` максимального кандидата);
- число отброшенных событий выборки аукциона.

Алерт: P95 выше 70 ms или доля таймаутов шлюза выше 1% за 5 минут. Это ещё до формального срыва 80 ms.
