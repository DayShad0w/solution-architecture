# Взаимодействие и протоколы

Диаграммы: [sequence-bid.puml](diagrams/sequence-bid.puml), [sequence-tracking.puml](diagrams/sequence-tracking.puml), [component-bidding.puml](diagrams/component-bidding.puml).

## Карта взаимодействий

| Граница | Протокол | Синхронно на пути ставки? |
| --- | --- | --- |
| DSP ↔ RTB API Gateway | HTTPS, OpenRTB 2.6 JSON | Да, это и есть контракт |
| Шлюз ↔ Bidding Service | HTTP/1.1 JSON внутри кластера, тот же BidRequest | Да, один короткий вызов |
| Bidding ↔ Redis | RESP | Только при промахе L1 или тесном бюджете, с жёстким таймаутом |
| Пользователь / DSP ↔ Tracking Ingress | HTTPS (пиксель, клик, `nurl`) | Нет, это другой запрос уже после аукциона |
| Tracking Ingress ↔ Kafka | Протокол Kafka, Avro | Да для приёма события, нет для аукциона |
| Кабинет ↔ Campaign / Finance / Analytics | HTTPS JSON | Нет |
| Campaign / Finance ↔ свои PostgreSQL | SQL | Нет |
| Изменения кампаний и стоп бюджета | Kafka, compacted-топики | Нет |
| Creative Delivery ↔ Redis | RESP при сохранении креатива | Нет |
| Finance ↔ платёжный шлюз | HTTPS API шлюза | Нет |

## Внешний протокол: OpenRTB поверх HTTPS

Партнёр уже описан в постановке как источник bid request и получатель bid response по OpenRTB. Менять контракт на gRPC нельзя: это внешняя система, и отрасль на этой границе говорит HTTP JSON.

Выбран OpenRTB 2.6, потому что в нём есть `tmax` — готовый бюджет времени запроса. Свой бинарный протокол «для скорости» отвергнут: выигрыш парсинга — единицы миллисекунд, цена — несовместимость с партнёром и отсутствие штатного no-bid.

No-bid — пустой `204`, как принято в OpenRTB. Тело с ошибкой на каждый нерелевантный запрос только увеличит трафик.

Аутентификация этой границы описана в [api-gateway.md](api-gateway.md): mTLS и список партнёров. Поверх открытого интернета без взаимной аутентификации OpenRTB не принимаем.

## Внутренний вызов шлюз → ставки: HTTP, не gRPC

Между шлюзом и сервисом ставок остаётся HTTP JSON, тот же документ OpenRTB без перекодирования. Причины:

- тело уже JSON, перевод в protobuf на каждом из 18 000 RPS тратит CPU и даёт второй контракт того же смысла;
- Envoy проксирует HTTP без транскодинга;
- один хоп, заранее известный дедлайн, пользы от мультиплексирования gRPC почти нет: запрос-ответ и так один.

gRPC здесь не ускоряет аукцион. Узкое место AS-IS — база, а не фреймворк RPC.

## Где gRPC уместен, и почему его мало

gRPC оправдан между своими сервисами, когда оба конца наши, вызовов много, контракт стабилен и важен размер сообщения. В этой системе такой пары на горячем пути нет.

Пакетный снимок кандидатов проектор забирает у системы учёта редкими страницами (раз в секунды, не на запрос пользователя). Для редкого объёмного чтения достаточно HTTPS. Отдельный gRPC «на будущее» между Campaign и Bidding плодит второй канал ради вызова, которого на ставке быть не должно.

Итог: **gRPC не используем ни на контуре DSP, ни между ставками и кампаниями.** Если позже появится внутренний высокочастотный контроль без готового JSON-контракта, решение пересмотрим отдельным ADR. Сейчас это был бы лишний runtime.

## Почему не REST между ставками и кампаниями на каждый запрос

REST на горячем пути отвергнут по той же причине, что и любой синхронный RPC: кампания не меняется 15 000 раз в секунду, а читать её 15 000 раз в секунду — повтор AS-IS, только вместо SQL будет HTTP. Обмен с кампаниями событийный: изменение уходит в Kafka, проекция оседает в Redis, ставки читают локальную копию.

REST остаётся на границе кабинета. Там человек, задержка в десятки и сотни миллисекунд нормальна, клиент — браузерный BFF на Node.js, отладка JSON проще, чем protobuf в журнале поддержки. Версии URL (`/v1/...`) достаточны.

## Почему Kafka для показов и кликов

Показ нельзя записывать синхронно в базу ставок и нельзя обрабатывать только одним потребителем. Нужен журнал:

- Tracking Ingress быстро принимает событие;
- Finance дочитывает его и проводит идемпотентное списание;
- загрузчик статистики дочитывает его в колоночное хранилище;
- отставший потребитель не заставляет аукцион ждать.

Обоснование отказа от RabbitMQ, Redis Streams и прямой записи в PostgreSQL — в [ADR-003](../Task1/adr/ADR-003-event-streaming.md).

Граница гарантий нарочно разная:

| Поток | Ждём подтверждения брокера до ответа клиенту? |
| --- | --- |
| Ответ DSP на bid request | Нет. Журнал аукциона — выборка после ответа |
| Пиксель показа, клик, win-notice | Да. Пока продюсер не получил ack от Kafka, пикселю не отвечаем успехом |

Иначе деньги опирались бы на best-effort буфер процесса ставок.

## Нужен ли API Gateway

Да, отдельный для DSP. Нет, общий на всю платформу.

Нужен, потому что аутентификация партнёра, лимит частоты, единый таймаут и размыкатель должны стоять перед процессом аукциона. Если вшить их в Bidding Service, больной или перегруженный аукцион перестанет сам себя защищать: ему же и принимать лишние соединения. Шлюз умеет ответить `204`, не занимая поток аукциона.

Не нужен один шлюз на кабинет и DSP. Отчёт рекламодателя и bid request делят тогда пул, лимиты и релиз конфигурации. Это возврат к проблеме монолита на уровне входа. У кабинета свой BFF. Внутренний восток-запад (проектор, потребители Kafka) через RTB-шлюз не ходит.

Почему Envoy, а не другой продукт — в [api-gateway.md](api-gateway.md).

## Последовательность ставки

1. Партнёр устанавливает mTLS и шлёт BidRequest.
2. Шлюз проверяет сертификат, лимит и оставшееся время. При нарушении сразу отвечает партнёру и не зовёт сервис.
3. Шлюз вызывает Bidding Service с дедлайном короче партнерского `tmax`.
4. Сервис считает ставку по L1/Redis либо отдаёт no-bid.
5. Шлюз возвращает этот ответ партнёру и пишет метрику времени.
6. Сервис, уже ответив, может положить выборку аукциона в Kafka.

## Последовательность показа

1. Плеер или браузер вызывает Tracking Ingress по URL из `adm` / `nurl`.
2. Ingress проверяет подпись URL (её подписал сервис ставок при сборке ответа), чтобы чужой показ не тратил бюджет.
3. Ingress публикует Avro-событие и ждёт ack.
4. Отвечает пикселю `200` или `204`.
5. Потребители Kafka независимо грузят ClickHouse и проводят списание.

Аукцион в этой последовательности не участвует.
