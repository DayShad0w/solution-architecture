# Надёжность контура ставок и денег

Базовый принцип: на пути 80 ms лучше быстрый no-bid, чем повтор и ожидание. На пути денег лучше повтор и идемпотентность, чем потеря или двойное списание. Это разные политики, их нельзя копировать из одного места в другое.

## Бюджет времени и таймауты

У каждого bid request есть дедлайн. Он считается на шлюзе и передаётся в сервис ставок заголовком. Сервис не начинает шаг, который заведомо не уложится в остаток.

| Шаг | Таймаут | Если не успели |
| --- | --- | --- |
| Весь запрос на шлюзе | не больше 70 ms и не больше `tmax` минус запас | `204` наружу, апстрим оборван |
| Чтение Redis с горячего пути | 2–4 ms, один раз | см. политику ниже по типу данных |
| Публикация выборки аукциона | не на запросе | сброс выборки |
| Публикация показа в Kafka | до 500 ms на Tracking Ingress | ошибка пикселю, партнёр или браузер повторит |

Внутри сервиса ставок нет каскада из нескольких сервисов, поэтому нечему устраивать цепочку таймаутов «каждый следующий чуть короче». Есть только Redis.

## Размыкатель

**Шлюз → копии ставок.** Outlier detection, подробно в [api-gateway.md](api-gateway.md). Открытый размыкатель означает `204`, а не очередь запросов.

**Сервис ставок → Redis.** Свой размыкатель в процессе:

- окно 5 секунд;
- открытие, если больше половины проверок бюджета (fail closed участок) не уложились в таймаут;
- в открытом состоянии большие остатки продолжают ставить по L1, тесные бюджеты получают no-bid `budget_unknown`;
- полуоткрытое состояние: пробные чтения раз в 100 ms.

Размыкатель к Campaign Service и Finance Service на этом пути отсутствует: вызовов нет, нечего размыкать. Это следствие границы сервиса, а не забытый паттерн.

Размыкатель Finance → платёжный шлюз живёт в финансовом сервисе и к аукциону отношения не имеет. Отказ оплаты не должен менять P95 ставок. Пополнение просто вернёт ошибку в кабинет.

## Повторы

| Вызов | Повтор |
| --- | --- |
| Шлюз → Bidding Service | Нет. Вторая попытка не укладывается в `tmax` и не идемпотентна относительно выборки |
| Bidding → Redis на горячем пути | Нет. Таймаут уже съел запас, повтор только растит хвост |
| Проектор → система учёта (снимок) | Да, с экспоненциальной паузой, вне горячего пути |
| Tracking Ingress → Kafka | Да, пока не кончился бюджет приёма пикселя: 3 попытки, паузы 20 ms, 50 ms, 100 ms, с дрожанием |
| Finance-потребитель → PostgreSQL | Да, с экспоненциальной паузой и верхней крышкой, сообщение не коммитится в Kafka, пока проводка не записана или не признана дублем |
| Finance → платёжный шлюз | Да, только с ключом идемпотентности шлюза, паузы от 1 s с верхней крышкой |

Экспоненциальная пауза используется там, где есть время и где повтор безопасен. На ответе DSP её нет.

## Идемпотентность финансовых операций

Источник истины о списании — журнал Finance Service, а не память аукциона.

Ключ проводки:

- показ: `impression:{impression_id}`;
- клик, если по модели за клик: `click:{click_id}`;
- пополнение: ключ, который возвращает или принимает платёжный шлюз.

`impression_id` генерирует сервис ставок и подписывает в URL показа. Повтор пикселя, повтор Kafka «хотя бы один раз» и повтор потребителя сходятся в одну строку журнала. Уникальное ограничение в PostgreSQL отклоняет вторую проводку, потребитель считает это успехом и сдвигает offset.

Операции журнала только добавляются. Баланс — свёртка журнала или обновление в той же транзакции, что и вставка проводки. Исправление — компенсирующая запись, не правка старой суммы.

Пополнение бюджета: кабинет получает ключ операции до вызова шлюза. Повтор кнопки и повтор запроса к шлюзу ссылаются на тот же ключ.

Аукцион сам по себе денег не двигает. Повтор bid request с тем же `id` гасится на шлюзе коротким кэшем ответа и не создаёт вторую проводку, потому что проводка родится только из показа.

## Запасные стратегии ставок

Порядок такой: ответить из локальных данных, иначе отказаться. «Дефолтная ставка наугад» почти всегда хуже no-bid: она тратит бюджет вслепую и может нарушить правила аукциона.

| Сбой | Поведение |
| --- | --- |
| Нет кандидатов в L1, Redis успел | Ответ из Redis, заполнение L1 |
| Нет кандидатов и Redis не успел | `204`, причина `cache_miss_deadline` |
| Проекция старше 5 минут | `204` для затронутых кампаний, алерт. Торговать заведомо устаревшим таргетингом не будем |
| Жёсткий стоп бюджета | `204`, причина `stopped` |
| Остаток бюджета неизвестен (тесный бюджет и Redis недоступен) | `204`, причина `budget_unknown` |
| Остаток большой, Redis недоступен, L1 свежий | Ставка по L1. Частотное ограничение пропускаем |
| Не успеваем в дедлайн до аукциона | `204`, причина `deadline` |
| Все копии ставок нездоровы | Шлюз отвечает `204`, не придерживая соединения |
| Нет заранее собранного `adm` | Кандидат отбрасывается. Собирать шаблон на запросе запрещено |

Кэшированная ставка допустима только как свежая проекция в L1/Redis, а не как одна глобальная цена «на всякий случай». Глобальный дефолт не вводим: у разных кампаний разные потолки, и один дефолт либо сливает бюджет, либо не выигрывает ничего.

## Изоляция

- Пул соединений и лимиты RTB-шлюза не общие с BFF кабинета.
- Tracking Ingress — отдельные процессы от Bidding Service, чтобы всплеск пикселей не отъедал CPU аукциона.
- Потребители Kafka не делят поток выполнения со ставками.
- Аналитические запросы не имеют доступа к базе, которую читает горячий путь. На переходе это read replica, в цели года — другой движок.

## Чего эта политика не обещает

No-bid в открытом размыкателе защищает от штрафа за медленные ответы, но партнёр всё равно видит падение доли побед. Это лучше простоя с таймаутами, и это нужно прямо проговорить в договоре: штатный `204` не считается деградацией latency. Если договор считает любой `204` простоем, пороги лимита и размыкателя придётся пересмотреть вместе с бизнесом — технически «всегда отвечать ставкой» при отказе данных нельзя.
