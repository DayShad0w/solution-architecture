# Стратегия данных

Диаграмма: [diagrams/data-architecture.puml](diagrams/data-architecture.puml).

Принцип: у сервиса одна система учёта, и горячий путь ставок этой системой не является. Общий PostgreSQL монолита остаётся только на переходные месяцы и только за антикоррупционным проектором.

## Сводка

| Сервис | Тип хранилища | Система учёта чего |
| --- | --- | --- |
| Сервис ставок | Нет БД учёта. L1-память и Redis как воспроизводимая проекция | Ничего. Кампании и деньги лежат у других сервисов |
| Сервис кампаний | PostgreSQL | Реклама: кампании, line items, таргетинг, потолки ставок, метаданные креативов |
| Сервис статистики | Kafka как журнал приёма, ClickHouse как учёт событий | Показы, клики, win-notice |
| Сервис аналитики | ClickHouse, отдельная база витрин | Отчёты. Сырые события не переписывает |
| Сервис финансов | PostgreSQL | Журнал проводок, балансы, счета |

Ниже — почему тип именно такой и почему соседний не подошёл.

## Сервис ставок

Своя PostgreSQL или своя колоночная база на пути ответа вернули бы синхронное чтение, из-за которого P95 сегодня 110–120 ms. Данные, нужные для выбора победителя, уже есть в сервисе кампаний и в финансовом журнале. Сервис ставок хранит денормализованную копию в Redis и в памяти процесса. Копию можно выбросить и собрать снова.

Журнал выборки аукционов — топик Kafka, не таблица. Потеря выборки не теряет деньги и не теряет кампании.

Почему не in-memory база класса отдельного кластера только под ставки: Redis уже нужен для общего остатка бюджета и частоты между копиями. Второй движок в памяти команда без SRE не окупает.

## Сервис кампаний

PostgreSQL. Кампания — связанные сущности с ограничениями целостности: рекламодатель, кампания, line item, креатив, правила таргетинга. Обновления редкие на фоне 18 000 RPS, зато каждая запись должна быть согласована. Реляционная модель и транзакция это закрывают. Горизонтально резать эту базу в горизонте года не нужно (см. [scaling.md](scaling.md)).

Почему не MongoDB и не «документы в Redis как учёт»: целостность связей и удобные выборки кабинета слабее, а выигрыша по нагрузке нет — нагрузка записи здесь низкая. Почему не ClickHouse: кампанию правят точечно, это не журнал.

## Сервис статистики

События — поток добавлений без обновления старой строки. Писать их в PostgreSQL значит повторить текущий write bottleneck. Учёт — ClickHouse: пакетная вставка, сжатие, разрезы по времени и кампании.

Перед ClickHouse стоит Kafka. Сервис приёма не ждёт вставку в колоночное хранилище, а хранилище можно перелить с offset, если загрузчик ошибся.

Почему статистике не хватает «той же PostgreSQL с партициями»: партиции облегчают удаление старого, но не убирают конкуренцию с финансами и не дают дешёвые аналитические сканы на объёме года.

## Сервис аналитики

Тоже ClickHouse, но другая база и другие таблицы: суточные и часовые витрины, а не сырой поток. Сервис аналитики только читает. Пишет загрузчик статистики через materialized view либо отдельный сборщик витрин.

Так выполняется формулировка «своя база у сервиса»: отдельные базы, пользователи и квоты внутри одного кластера на старте. Физически разнести кластеры можно, когда отчёты начнут мешать загрузке сырых событий. Для команды без SRE один управляемый кластер честнее, чем два недосмотренных. Логическая граница при этом уже есть, и запросы кабинета не ходят в таблицы сырого приёма напрямую, если витрина построена.

Почему не read replica PostgreSQL как цель года: реплика нужна в первые недели, чтобы снять боль, но тяжёлые отчёты на строковом хранилище при росте событий снова упрутся в диск. Реплика — переход, не цель.

## Сервис финансов

PostgreSQL. Проводка, баланс и счёт должны зафиксироваться вместе. Нужны уникальный ключ идемпотентности, транзакция и предсказуемое чтение «сколько денег осталось» для сверки. Это сильная сторона реляционной СУБД, а не колоночного движка.

Почему не списывать прямо в Redis: кэш можно потерять вместе с остатком, и не останется журнала для сверки со счетами. Redis держит только оценку остатка для pacing. Расхождение лечится сверкой с журналом, а не объявлением Redis бухгалтерией.

Почему не одна база с кампаниями «чтобы было проще джойнить»: тогда отчётный или рекламный релиз снова делит диск и окно обслуживания с деньгами. Связь рекламодателя передаётся идентификатором, джойн через границу сервисов не делаем. Кабинет склеивает ответ двумя запросами.

## Переходные компромиссы первых трёх месяцев

| Данные | Где лежат в первой поставке | Когда переезжают |
| --- | --- | --- |
| Кампании и бюджеты как учёт | PostgreSQL монолита | Вместе с Campaign и Finance сервисами |
| Проекция для нового аукциона | Redis | Остаётся, меняется только источник снимка |
| События новой DSP | Kafka → можно временно не иметь ClickHouse, если потребитель пишет в отдельную схему и не в primary аукциона | ClickHouse, как только отчёты по новой DSP нужны в кабинете |
| Отчёты старых клиентов | Read replica монолита | ClickHouse |

Даже временная запись событий новой DSP в primary монолита запрещена: ради этого и ставится очередь.
