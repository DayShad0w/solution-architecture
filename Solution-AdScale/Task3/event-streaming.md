# Потоковая обработка

Решение о брокере и Avro: [ADR-003](../Task1/adr/ADR-003-event-streaming.md). Диаграмма: [diagrams/kafka-topology.puml](diagrams/kafka-topology.puml). Последовательность показа: [задание 2](../Task2/diagrams/sequence-tracking.puml).

Кластер — управляемый Kafka, фактор репликации 3, `min.insync.replicas=2`. Продюсер события показа ждёт ack всех in-sync реплик (`acks=all`).

## Топики

| Топик | Ключ раздела | Кто пишет | Зачем |
| --- | --- | --- | --- |
| `tracking.impressions` | `event_id` | Tracking Ingress | Факт показа, источник списания по модели CPM |
| `tracking.clicks` | `event_id` | Tracking Ingress | Факт клика |
| `tracking.wins` | `event_id` | Tracking Ingress | Win-notice, если партнёр сообщает победу отдельно от показа |
| `campaign.lifecycle` | `campaign_id` | Campaign Service или проектор на переходе | Изменения учёта рекламы. Compacted |
| `budget.snapshots` | `campaign_id` | Finance Service | Остаток и флаг остановки. Compacted |
| `rtb.auction` | `request_id` | Bidding Service | Выборка аукционов для разбора. Не источник денег |

Ключ `event_id`, а не `campaign_id`, у событий показа: большая кампания не должна прибить один раздел. Порядок по кампании для проводок не нужен, потому что идемпотентность держится на ключе проводки, а не на порядке сообщений.

`campaign_id` у compacted-топиков уместен: на ключ хранится последняя версия конфигурации, и потребителю проекции нужна именно она.

## Схема событий

Формат — Avro, реестр схем, совместимость BACKWARD. JSON отклонён в ADR-003: несколько потребителей и эволюция полей.

Обязательные поля событий трекинга:

| Поле | Зачем |
| --- | --- |
| `event_id` | Ключ идемпотентности |
| `event_type` | impression / click / win |
| `occurred_at` | Время на источнике |
| `partner_id` | Чей трафик |
| `campaign_id`, `line_item_id`, `creative_id` | Связь с учётом |
| `price_micros` | Цена, которую согласуем со списанием |
| `request_id` | Связь с bid request без тела запроса |
| `user_key` | Уже усечённый ключ частоты, не сырой идентификатор устройства в открытом виде |

Тело OpenRTB в топик не кладём. Для расследования хватает выборки `rtb.auction` с урезанным набором полей и отдельным коротким ретеншеном.

Новое необязательное поле добавляется со значением по умолчанию. Переименование и смена смысла — новая версия топика (`tracking.impressions.v2`), а не тихая правка. Потребители финансового журнала не обновляются в ту же минуту, что и продюсер, поэтому ломать старое чтение нельзя.

## Группы потребителей

| Группа | Топики | Что делает | Коммит offset |
| --- | --- | --- | --- |
| `finance-ledger` | impressions, clicks | Идемпотентная проводка | После записи в PostgreSQL или признания дубля |
| `stats-loader` | impressions, clicks, wins | Пакет в сырые таблицы ClickHouse | После успешной вставки пакета |
| `bidding-projector` | `campaign.lifecycle`, `budget.snapshots` | Обновление Redis и канала инвалидации | После записи ключей |
| `auction-debug` | `rtb.auction` | Разбор инцидентов, можно отставать и выключать | Best effort |

У каждого потребителя своя группа. Общий offset запрещён: отставание аналитической заливки не должно останавливать деньги, и наоборот.

Повторная обработка — нормальный режим. Все группы идемпотентны. `stats-loader` вставляет блоками с дедупликацией по `event_id` (движок ReplacingMergeTree или эквивалент управляемого кластера). `finance-ledger` опирается на уникальный ключ проводки.

Отдельный Flink не вводим. Преобразования простые: положить событие в таблицу, положить проводку, обновить ключ кэша. Ещё один кластер без SRE не улучшит эти три задачи.

## Хранение

| Топик | Политика | Почему |
| --- | --- | --- |
| `tracking.*` | 7 суток | За это окно загрузчик и финансовый потребитель обязаны догнать отставание, включая повторную заливку ClickHouse. Дольше держать сырой поток дорого, учёт уже в базах |
| `campaign.lifecycle`, `budget.snapshots` | Compacted, без удаления последней версии по времени | Проектор и новый регион поднимают состояние с лога |
| `rtb.auction` | 24 часа, выборка не 100% трафика | Диагностика, не учёт |

Если лаг `finance-ledger` превышает 1 час, это инцидент, хотя до удаления данных ещё есть запас суток. Ждать конца ретеншена нельзя: вместе с лагом растёт окно, в котором pacing опирается на оценку, а не на факт.

Разделов на `tracking.impressions` закладываем с запасом под пик года: ориентир — десятки разделов, чтобы 50 000 RPS ставок и более редкие, но всё ещё крупные потоки показов не упирались в один раздел. Точное число уточняется на прогоне (цель — держать раздел заметно ниже потолка пропускной способности одного потребителя в группе). На трёхмесячном срезе разделов меньше, увеличивать число разделов можно без смены контракта, уменьшать — нельзя, поэтому стартуем не с одного.

## Второй регион

В горизонте года у каждого региона свой кластер приёма показов, чтобы пиксель не ждал чужую зону. Финансовый журнал остаётся в основном регионе: потребители региональных кластеров через зеркало (MirrorMaker 2 или аналог управляемой услуги) стекаются в `finance-ledger` основного региона. Идемпотентный ключ делает двойную доставку зеркала безопасной.

Конфигурационные compacted-топики зеркалируются в обе стороны с одним владельцем записи на тип сущности, чтобы два региона не переписывали одну кампанию. Владелец записи кампании и денег — основной регион, пока финансы active-passive.
