# Отказоустойчивость данных

Цифры ниже — целевые для схемы года. В первые три месяца второй регион ещё не обещан: отказ единственного региона остаётся принятым риском, внутри региона отказ одной зоны — уже нет.

Доступность 99,9% относится к контуру ответа на ставку (включая штатный no-bid), а не к кабинету и не к свежести отчёта.

## RPO и RTO

| Сервис и данные | RPO | RTO | Как достигается |
| --- | --- | --- | --- |
| Ставки, вычислительный контур | 0 относительно учёта: своего учёта нет | Минуты на возврат доли трафика в регионе, в цели года второй регион принимает трафик сразу | Копии без состояния, шлюз снимает больную копию. Потеря процесса не теряет кампании |
| Проекция Redis | Минуты (возраст последнего снимка). Учёт не теряется | До 15 минут на полную пересборку региона из учёта | Redis не бэкапим как книгу. Проектор перечитывает Campaign DB и журнал остатков |
| Campaign PostgreSQL | Около 0 для подтверждённой транзакции (синхронная реплика) | До 15 минут на переключение primary в другой зоне | Реплика + PITR из архива WAL, если отказали обе копии зоны |
| Finance PostgreSQL | Около 0 для подтверждённой проводки | До 15 минут на переключение primary | Синхронная реплика, архив WAL, запрет автоматического failover при подозрении на расщепление |
| События в Kafka | 0 для сообщения, получившего ack | Часы на потерю целого кластера при живом зеркале или повторном приёме; внутри региона минуты | Фактор 3. Показ не подтверждён клиенту, пока ack не получен, поэтому клиент повторит |
| ClickHouse статистики | До окна лага загрузчика, практически минуты. Повторная заливка из Kafka в пределах 7 суток даёт RPO 0 относительно журнала | До 4 часов на восстановление шарда из реплики или объектного хранилища | Реплика каждого шарда. Журнал Kafka первичен на окне ретеншена |
| Витрины аналитики | Часы допустимы | До суток на пересборку витрин из сырых таблиц | Отчёт не на критическом пути. Витрина — производное |

RPO финансов «около 0» означает: проводка, на которую клиент получил успех, переживает отказ одной зоны. Не означает сохранность денег, которые существуют только в Redis. Поэтому Redis не подтверждает списание.

## Что происходит при типовых отказах

**Одна копия ставок.** Шлюз исключает её. Остальные продолжают. Данные не восстанавливаем.

**Redis региона недоступен.** Большие бюджеты ещё какое-то время ставятся из L1, тесные получают no-bid, частота не проверяется. Если проекция протухает, регион переходит в сплошной no-bid. Параллельно проектор собирает снимок из учёта. Кабинет и деньги работают.

**Primary кампаний недоступен.** Переключение на синхронную реплику. Аукцион это не чувствует, пока Redis жив. Кабинет на короткое время не сохраняет правки.

**Primary финансов недоступен.** Новые проводки ждут переключения, offset Kafka не коммитится, события не теряются. Аукцион продолжает pacing по последнему остатку и по флагу stop. Окно перекрута ограничено политикой pacing из задания 2. После подъёма журнала сверка сравнивает сумму проводок и сумму событий.

**Загрузчик ClickHouse отстал.** Отчёты стареют. `finance-ledger` не делит с ним группу и не останавливается. Догрузка — продолжение с offset.

**Регион целиком, горизонт года.** DNS или глобальный вход новой DSP смотрит на второй регион, где ставки уже прогреты. Финансы остаются в основном регионе; если недоступен и он, приём показов во втором регионе копится в локальной Kafka до возврата журнала. Ставки второго региона работают по последней приехавшей проекции и перестают торговать, когда проекция старше порога. Так регион не тратит бюджет вслепую сутками.

## Резервные копии

| Данные | Копия | Срок хранения |
| --- | --- | --- |
| Finance PostgreSQL | Непрерывный архив WAL и ежедневный базовый снимок, копия в другом регионе в цели года | 30 дней PITR |
| Campaign PostgreSQL | Архив WAL и ежедневный снимок | 14 дней |
| ClickHouse | Реплика шарда плюс периодический снимок в объектное хранилище | 14 дней для сырых таблиц, витрины можно пересобрать |
| Kafka | Репликация, не файловый бэкап как основной механизм | Ретеншен топика |
| Redis | Не бэкапим как учёт. Необязательный RDB только чтобы ускорить прогрев | Сутки, можно выбросить |
| Секреты и сертификаты партнёров | Хранилище секретов кластера, не репозиторий | По политике ротации |

Восстановление финансов из PITR прогоняется по расписанию на отдельном инстансе, иначе бэкап считается непроверенным. После восстановления обязательна сверка: число проводок и сумма против повторного чтения Kafka за тот же интервал.

Удаление кампании и запрос человека на удаление персональных идентификаторов не прячем внутрь бесконечного журнала. В событиях трекинга нет сырого устройства, только `user_key`. Сырой OpenRTB в топики не пишется.

## Соответствие 12 факторам

Факторы относятся к сервисам контура (ставки, приём событий, проектор, финансы, кампании), не к самому PostgreSQL.

| Фактор | Как выполнен |
| --- | --- |
| Одна база кода | Сервис — отдельный репозиторий или отдельный модуль с одним процессом сборки. Монолит больше не тащит новый путь |
| Зависимости | Явный манифест, сборка в образ. На сервере ничего не доустанавливаем руками |
| Конфигурация | Адреса брокера, Redis и базы, идентификаторы партнёров и пороги дедлайна — в окружении и секретах, не в коде |
| Сторонние службы | PostgreSQL, Redis, Kafka, шлюз оплаты подключаются по URL. Сервис ставок не отличает «свою» базу, потому что её нет |
| Сборка, релиз, запуск | Образ неизменяем. Выкладка меняет образ и конфигурацию, а не патчит процесс |
| Процессы | Копии ставок и приёма не хранят учёт. Локальный L1 можно выбросить |
| Привязка к порту | HTTP слушает порт, шлюз забирает readiness. Самостоятельный демон без порта для ставок не нужен |
| Параллелизм | Масштаб — число копий. Внутри процесса аукцион не держит глобальную блокировку на кампанию |
| Утилизируемость | Быстрый старт после прогрева и быстрая остановка: шлюз снимает вес, процесс досылает буфер выборки и выходит. Показный продюсер не подтверждает событие, которое не попало в брокер |
| Подобие сред | Тот же образ в прогоне 18 000 RPS и в бою. Отличается конфигурация размера |
| Логи | Процессы пишут в stdout. Сборщик кластера увозит их наружу. Файловый журнал на диске копии не используем |
| Административные задачи | Пересборка снимка, сверка журнала, повторная заливка ClickHouse — отдельные запуски, не крон внутри процесса аукциона |

Ручной деплой монолита этим факторам не соответствует. Новый путь с первого релиза выпускается образом и конфигурацией, иначе откат партнёра на шлюзе будет быстрее, чем откат самого сервиса.
