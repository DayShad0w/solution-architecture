# Масштабирование хранилищ

Цель мощности: 18 000 RPS на новом пути через три месяца и 50 000 RPS пика ставок через год. Хранилища масштабируются по-разному, потому что у них разный профиль. Диаграмма проекций: [diagrams/cache-and-cqrs.puml](diagrams/cache-and-cqrs.puml).

## Где master-replica

Речь о PostgreSQL: одна основная копия принимает запись, реплики принимают чтение и готовы стать основными.

| Хранилище | Схема | Зачем |
| --- | --- | --- |
| Campaign DB | Один primary, синхронная реплика в другой зоне, асинхронные реплики для кабинета | Запись редкая, читать кабинет может с реплики. Синхронная реплика нужна для автоматического failover без потери подтверждённой кампании |
| Finance DB | Один primary, синхронная реплика, без чтения отчётов с этой пары | Деньги не масштабируем чтением аналитики. Реплика существует ради отказа зоны, а не ради RPS |
| PostgreSQL монолита на переходе | Primary + одна read replica | Уже в первые недели, чтобы отчёты ушли с диска аукциона |

Ставки в эту схему не входят: у них нет primary-базы.

ClickHouse масштабируется репликами шардов, это не пара master-slave в смысле одной записи. См. ниже.

## Что шардировать и по какому ключу

| Данные | Шард | Ключ | Почему такой ключ |
| --- | --- | --- | --- |
| Сырые показы и клики в ClickHouse | Да, с первого кластера | `cityHash64(event_id)` плюс партиция по дате | События независимы. Ключ кампании собрал бы всю большую кампанию на один шард |
| Витрины аналитики | Да, если кластер общий с сырьём — те же шарды | Дата и `campaign_id` на уровне партиции таблицы, не обязательно отдельный шард | Отчёт почти всегда режет по времени и кампании |
| Redis частоты и индексов | Redis Cluster | Хеш ключа (`freq:...`, `cand:...`) | Ключи мелкие и независимые, горячая кампания не должна требовать отдельного ручного шарда |
| Campaign PostgreSQL | Нет в горизонте года | — | Объём записи — действия людей в кабинете, не 50 000 RPS |
| Finance PostgreSQL | Нет в горизонте года. Партиция журнала по месяцу | Партиция по времени, не шард по `advertiser_id` | Партиция упрощает хранение и сверку. Шард по рекламодателю понадобится только если один primary перестанет принимать проводки. До этого рано: проводка рождается из показа, но это не 50 000 транзакций, если писать пакетами потребителя |

Шардировать финансы «на вырост» в первые три месяца вредно: кросс-шардовые проводки и сверка без SRE дороже, чем честный потолок одного primary. Порог пересмотра: устойчивая загрузка CPU primary выше 60% на пакете проводок или задержка применения журнала выше минуты.

Kafka шардируется разделами, это разобрано в [event-streaming.md](event-streaming.md). Ключ раздела события — `event_id`, по той же причине, что и шард ClickHouse.

## Read replica для аналитики

На переходе — да, PostgreSQL replica, только для старых отчётов.

В целевой схеме отдельная read replica PostgreSQL под аналитику не используется. Аналитика читает витрины ClickHouse, у которых свои реплики шардов. Реплика строковой базы не выдержит те же сканы и снова свяжет отчёт с операционным диском, пусть и не с диском денег.

У кампаний read replica остаётся, но её читает кабинет при открытии карточек, а не движок отчётов.

## CQRS

Два места, где модель записи и модель чтения — разные структуры. Оба показаны на [diagrams/cache-and-cqrs.puml](diagrams/cache-and-cqrs.puml).

**Ставки.** Запись — нормализованные таблицы Campaign и журнал Finance. Чтение аукциона — `BidCandidate`, индекс по площадке и остаток в Redis. Синхронизация — поток изменений и снимок, не джойн на запросе. Это CQRS ради задержки: читать ту же таблицу, куда пишет кабинет, на 50 000 RPS нельзя.

**Аналитика.** Запись — поток событий в Kafka и сырые таблицы ClickHouse. Чтение — витрины по кампании и часу. Сервис аналитики не читает сырой поток и не пишет в витрину из запроса пользователя. Материализованное представление обновляется по мере вставки. Это CQRS ради изоляции тяжёлого чтения от приёма событий.

Где CQRS не нужен:

- финансы: кабинет и сверка читают тот же журнал, что и потребитель. Вторая модель чтения «баланс в Elasticsearch» добавит расхождения без выигрыша для SLA;
- приём OpenRTB: запрос не является командой записи учёта.

## Масштаб stateless-слоя рядом с данными

Хранилища не вытянут SLA, если сами ставки нельзя умножить. Копии Bidding Service не держат шарда. Горизонтально добавляются процессы, каждый с прогретым L1. Узкое место, за которым следим при 50 000 RPS, — не PostgreSQL кампаний, а CPU аукциона, память индексов и число операций Redis на промахе L1. Поэтому L1 обязателен: без него 50 000 RPS стали бы 50 000 чтений Redis на запрос.
