# Задание 3.3. API для мобильного приложения (OpenAPI)

**Цель:** разработать спецификацию OpenAPI для ключевого endpoint — получения пациентом списка своих предстоящих записей к врачу.

Спецификация: [`appointments-openapi.yaml`](appointments-openapi.yaml).

## Что описано

- **Ресурс и метод:** `GET /api/v1/appointments` — чтение коллекции записей текущего пациента.
- **Фильтрация:** параметр `status` (`upcoming` по умолчанию, также `past`, `cancelled`, `all`).
- **Пагинация:** `limit` (1–100, по умолчанию 20) и `offset` (≥0, по умолчанию 0).
- **Аутентификация:** `bearerAuth` — access-токен JWT в заголовке `Authorization: Bearer <token>`, выданный Identity Provider (OAuth2/OIDC).
- **Коды ответов:** `200` (список + метаданные пагинации), `401` (нет/недействителен токен), `500` (внутренняя ошибка, с `traceId`) — каждый с примером.

## Комментарий: подход к пагинации и версионированию

**Пагинация — offset/limit.** Для этого endpoint выбрана offset-пагинация: она проста в реализации и на клиенте, понятна и достаточна для списка записей одного пациента (объём данных небольшой). Клиент получает `total`, поэтому может показать общее число и номера страниц. Компромисс: при больших, часто меняющихся наборах offset даёт эффект «съезжающих» страниц и деградирует на глубоких смещениях (БД всё равно сканирует пропущенные строки). Поэтому для крупных растущих коллекций (например, глобальная лента событий или история всех операций) в будущем выбирается **cursor-based**-пагинация (keyset по `startsAt`+`id`): стабильнее при вставках и эффективнее на больших объёмах. Для «моих записей» выгода cursor несущественна, а цена сложнее — отсюда выбор offset.

**Версионирование — в URL (`/api/v1/...`).** Версия в пути выбрана как самый явный и предсказуемый для мобильных клиентов способ: версия видна в логах и трассировке, легко маршрутизируется на API Gateway, разные версии можно катить параллельно во время миграции приложения. Это особенно важно в кейсе «Здоровье+», где сотрудники жалуются на нестабильность и отсутствие документации контрактов (Алексей, задание 3.3): жёсткий контракт с версией в URL даёт обратную совместимость — ломающие изменения выходят как `/api/v2`, а старые клиенты продолжают работать на `/api/v1`. Альтернативы (версия в заголовке или media-type) гибче, но менее наглядны и хуже кэшируются/маршрутизируются.

> Примечание: в постановке упомянут OpenAPI 3.2; спецификация оформлена в стабильной версии 3.0.3 как наиболее поддерживаемой инструментами (Swagger UI, кодогенераторы). Синтаксис параметров, схем и security при переходе на 3.1/3.2 не меняется.
