# Задание 4.2. Стратегия горизонтального масштабирования

**Цель:** определить две наиболее критичные ИТ-системы и разработать для них план горизонтального масштабирования под новую нагрузку.

## Контекст (из материалов)

Цель финала — 50 000 пользователей в часы пик при отклике < 1 с для 99% запросов и доступности 99.95%. Legacy-системы (1С, LIS) горизонтально не масштабируются и выносятся за кэш/события (Task4.1, Task3.1). Среди систем, которые масштабировать можно и нужно, самые критичные под новую нагрузку — **Расписание** (ядро главного сценария, запись + чтение слотов, уже страдает от блокировок — INT-009, Дмитрий) и **CRM** (хранит и отдаёт результаты анализов и карточки, ключевой сценарий «посмотреть анализы» — большой объём чтений).

Обе — stateless-сервисы на Java с PostgreSQL, что позволяет горизонтальное масштабирование по принципам из урока: stateless-приложение за балансировщиком + масштабирование слоя данных.

## Таблица масштабирования

| ИТ-система | Реализация горизонтального масштабирования | Ключевое ограничение метода | Решение для ограничения |
| --- | --- | --- | --- |
| **Расписание** | Сделать слой приложения stateless и запустить N реплик за балансировщиком (autoscaling по нагрузке); чтение слотов — с read-реплик PostgreSQL; шардирование данных по клинике/городу (Москва, СПб, Екатеринбург, Новосибирск). | **Конкуренция на запись и блокировки «горячих» слотов**: бронь одного слота — это write в одну строку; реплики приложения не устраняют contention на таблице слотов (как раз блокировки из INT-009 и интервью Дмитрия). Запись всё равно идёт в один primary-узел БД. | Убрать блокировки: бронь через **оптимистичную блокировку** (version/CAS) или быстрый резерв слота в in-memory store (Redis) с идемпотентным ключом и последующей фиксацией; шардирование по городу распределяет записи по независимым узлам. Это снимает lock contention и позволяет масштабировать запись. |
| **CRM** | Stateless-реплики за балансировщиком; **CQRS**: тяжёлые чтения (анализы, карточки) идут в read-модель/кэш, наполняемую событиями из Lab Results Service; read-реплики PostgreSQL для остальных чтений. | **Лаг репликации и нарушение read-your-writes**: после записи реплика ещё не содержит свежие данные, пациент/врач может увидеть устаревший результат (а кейс и так про «неактуальные анализы» — INT-011). | Критичные «только что записанные» чтения направлять на primary (read-your-writes routing); инвалидация кэша по событию обновления результата; для некритичных чтений допускать eventual consistency. Так масштабируем чтение, не показывая устаревшие данные там, где это важно. |

## Пояснение

Горизонтальное масштабирование безопасно работает только на stateless-компонентах: состояние (сессии, корзины саги) выносится в общий store, тогда реплики взаимозаменяемы за балансировщиком. Узкое место при этом смещается на слой данных — отсюда в обеих системах главная работа не в добавлении реплик приложения, а в развязке записи (Расписание) и чтения (CRM) на уровне БД. Это прямо отвечает на болевые точки из материалов: блокировки слотов и неактуальные анализы.
