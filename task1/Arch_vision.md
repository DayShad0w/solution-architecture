# Архитектурное видение: Цифровая продажа алмазов («Diamond Universe»)
## 1. Задача
**Проблематика:**
Бизнесу требуется экстренная трансформация классического (офлайн) процесса реализации алмазов в цифровой формат. Необходимо внедрить сквозной бизнес-процесс оценки (оцифровки) сырья с привлечением внешней лаборатории и организовать безопасный цифровой канал сбыта (онлайн-аукцион) с минимальным Time-to-Market.
**Кому и чем помогает решение:**
*   **Владельцы бизнеса:** Восстановление объемов продаж, диверсификация каналов сбыта, снижение издержек на проведение офлайн-мероприятий.
*   **Покупатели:** Получение доступа к торгам из любой точки мира с предоставлением исчерпывающего цифрового профиля каждого камня (гарантия качества без физического присутствия).
*   **Операционные подразделения (Логистика, Бухгалтерия):** Автоматизация маршрутизации логистики и выставления актов, минимизация ручного труда и ошибок пересортицы.
**Значимость:**
Реализация задачи критически важна для сохранения рыночных позиций компании в условиях глобальных ограничений. Отсутствие цифрового канала сбыта ведет к прямой потере выручки и заморозке активов.
## 2. Контекст
**Предпосылки возникновения:**
Пандемия COVID-19 и последующие локдауны полностью парализовали традиционный формат оценки и продажи алмазов. Индустрия вынужденно переходит в онлайн, что требует немедленной адаптации ИТ-инфраструктуры к новым реалиям с учетом высоких затрат на логистику.
**Текущее состояние (AS-IS):**
Текущий ИТ-ландшафт имеет высокую степень фрагментации.
*   Внутренние системы (ИС «Алмазы», ИС «Логистика», ИС «Бухгалтерия», ИС «Аукцион») не образуют единого информационного пространства.
*   ИС «Аукцион» не имеет внешнего веб-интерфейса.
*   ИС «Лаборатория» полностью изолирована во внешнем контуре. Присутствует серьезный информационный разрыв (Data Gap): система не отслеживает статус и местонахождение сырья в момент передачи стороннему контрагенту.
**Целевое состояние (TO-BE):**
Единая интеграционная шина (или API Gateway), обеспечивающая бесшовный обмен данными между внутренними ИС и внешними подрядчиками. Реализация концепции Single Source of Truth (Единый источник истины) для каждого камня на всем его жизненном цикле.
**Ограничения проекта:**
*   **Временные:** Запуск первой версии (MVP1) через 2 месяца.
*   **Ресурсные:** Минимальное вмешательство в Core-системы на первом этапе.
*   **Регуляторные:** Строгий государственный контроль (необходимость трекинга каждого экземпляра, наличие электронных паспортов, сертификатов, метрологических заключений).
*   **Информационная безопасность:** Высокие риски утечки коммерческой тайны (данных оценки) и угрозы перехвата данных при передаче между внешней лабораторией и внутренним контуром.
* **Зависимость от контрагента (Vendor Lock-in) и SLA:** Отсутствие контроля над циклом разработки ИС «Лаборатория». Риск изменения форматов данных на стороне партнера и отсутствие гарантированного уровня обслуживания (SLA) для внешнего API.
## 3. Описание оптимального решения
Для соблюдения жестких сроков и минимизации рисков предлагается двухэтапный инкрементальный подход к архитектуре.
### Этап 1: Тактическое решение (MVP v1 — запуск через 2 месяца)
Цель данного этапа — запустить процесс «как есть» инструментами No-Code/Low-Code и временными "костылями" (workarounds) без вмешательства в исходный код критичных ИС.
*   **ИС «Алмазы»:** Использование штатного функционала. Формирование пула алмазов для торгов производится путем выгрузки утвержденных шаблонов Excel. Файл выступает временным транзитным хранилищем.
*   **ИС «Логистика»:** Ручная настройка новых маршрутных листов (офис ↔ лаборатория) в рамках имеющегося функционала.
*   **Организация торгов:** Развертывание Private Cloud (IaaS). Публикация данных для покупателей осуществляется в защищенном облачном хранилище с применением строгих политик контроля доступа (RBAC).
*   **Интеграция:** Передача данных от ИС «Лаборатория» производится пакетно через защищенный файловый обменник (SFTP) или зашифрованные email-контейнеры (PGP).
### Этап 2: Целевая архитектура (MVP v2 — полномасштабная автоматизация)
Отказ от транзитных файлов, реализация синхронных и асинхронных интеграций, устранение архитектурных и ИБ-рисков.
|**Информационная система**|**Архитектурные изменения и новые функции**|
|---|---|
|**ИС «Алмазы»**|Внедрение паттерна State Machine (статусная модель). Функции: жесткая блокировка экземпляра под аукцион, отслеживание статуса (в лаборатории/на складе/продан). Система становится MDM (Master Data Management) для сырья.|
|**ИС «Логистика»**|Реализация End-to-End трекинга. Интеграция событий доставки с ИС «Алмазы» по модели Event-Driven Architecture (EDA) для автоматической смены статусов камней.|
|**ИС «Аукцион»**|Разработка полноценного Frontend-портала. Интеграция с S3-совместимым объектным хранилищем для отдачи тяжелого медиаконтента (3D-модели, сканы) без нагрузки на основную БД.|
|**ИС «Лаборатория»**|Построение защищенного B2B-шлюза. Использование протокола Mutual TLS (mTLS) и VPN-туннеля для передачи результатов оцифровки по REST API напрямую в ИС «Аукцион» и ИС «Алмазы».|
|**ИС «Бухгалтерия»**|Настройка автоматического биллинга (начислений и актирования) через API-триггеры, поступающие от ИС «Логистика» (факт доставки) и ИС «Лаборатория» (факт выполнения оценки).|
#### Стратегия взаимодействия с внешней лабораторией
Для минимизации рисков интеграции с независимым контрагентом процесс согласования обмена данными делится на организационный и технический уровни:
* **Организационно-правовой уровень:**
	* Подписание **NDA** (соглашение о неразглашении) и **DPA** (Data Processing Agreement) до начала передачи любых спецификаций.
	* Фиксация **SLA (Service Level Agreement)** в контракте: определение времени доступности систем (Uptime), окон для технического обслуживания (Maintenance windows) и времени реакции на инциденты интеграции.
* **Технический уровень (MVP v1 - Ручной обмен):**
	* Утверждение на уровне регламента жестких структур файлов (например, XSD-схемы для XML или JSON Schema). Любое изменение структуры шаблона обмена со стороны лаборатории без предварительного согласования должно блокироваться на уровне валидатора на нашей стороне.
* **Архитектурный уровень (MVP v2 - Автоматизация):**
	* **Подход Contract-First:** Совместная разработка и подписание API-контракта (OpenAPI/Swagger) до написания кода интеграции. Лаборатория либо реализует API по нашему стандарту, либо предоставляет свой контракт, под который мы подстраиваемся.
	* **Anti-Corruption Layer (Антикоррупционный слой):** На стороне «Diamond Universe» (в рамках интеграционной шины или API Gateway) внедряется паттерн **Adapter (Адаптер)**. Внутренние системы (ИС «Алмазы», ИС «Аукцион») не должны работать с моделями данных лаборатории напрямую. Адаптер трансформирует внешние DTO (Data Transfer Objects) лаборатории во внутренний канонический формат компании. Это защитит ядро (Core-системы) от поломок при изменении API внешнего поставщика.
### 4. Векторы безопасности и отказоустойчивости
*   **Защита данных в покое и движении:** Все данные об оценке сырья должны шифроваться (AES-256). Взаимодействие с внешней ИС «Лаборатория» требует развертывания WAF (Web Application Firewall) для предотвращения инъекций и эксплуатации уязвимостей внешнего API.
*   **Целостность:** Присвоение каждому алмазу неизменяемого хеша на основе его физических характеристик после оцифровки. Это исключит риски подмены камня (пересортицы) на этапе логистики.
*   **Отказоустойчивость:** Размещение витрины ИС «Аукцион» за балансировщиком нагрузки (Load Balancer) с настройкой Auto-Scaling в приватном облаке для защиты от возможных DDoS-атак во время проведения торгов и обеспечения высокой доступности.
